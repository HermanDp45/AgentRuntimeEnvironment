# ADR-0007: запуск учебного сандбокса v0

- Статус: accepted для локального прототипа; не решение для публичного сервера
- Дата: 2026-11-06
- Связано: ADR-0005, ADR-0006; A-5, A-6

## Контекст

Нужно проверить контракты, отмену и файловые операции до харнеса и сетевого монтирования.
На машине уже работает Docker Desktop. Настоящей пользовательской папки в прототипе нет.

## Решение

Доверенный FastAPI-менеджер обращается к существующему Docker daemon через socket.
Socket доступен только менеджеру, не контейнерам агента. Менеджер запускается как root:
это устраняет различия GID сокета между Desktop и Linux CI, но оставляет ему права daemon.
API пока без авторизации, доступен только на loopback; наружу его публиковать нельзя.
Namespace один на менеджер, метка are.owner ограничивает область его очистки.

Сандбокс — фиксированный образ Python + shell + pytest, UID 10001, read-only root,
cap_drop ALL, no-new-privileges, seccomp builtin, закрытая сеть и ограничения ресурсов.
Образ собственного проекта собирается из исходников с закреплёнными базами и lock-файлом;
при старте менеджера разрешается в immutable image ID. Тег содержит имя проекта
Compose: параллельные проекты не перетирают образы друг друга. Административная
SANDBOX_IMAGE задаётся Compose, запрос пользователя не может её переопределить.
Ручная пересборка образа требует перезапуска менеджера.
Встроенный seccomp указан именно в Docker API: на проверенном Desktop daemon по умолчанию
использовал unconfined. Compose 2.30.3 трактует builtin как имя локального файла,
поэтому у доверенных Compose-компонентов остаётся профиль daemon; динамические сандбоксы
получают явный builtin и Seccomp: 2.

Временная /work — tmpfs 64 МиБ: даёт проверяемый ENOSPC без зависимости от storage driver.
Она содержит только синтетическую фикстуру, сохраняется между операциями и после cancel,
удаляется вместе с контейнером. Результат забирается collect до release.
Это промежуточное хранилище; оно не заменяет требуемое сетевое монтирование ADR-0002.

PID1 — маленький Python-supervisor с обработкой SIGTERM и сбором потомков.
Отмена использует kill(-1, SIGKILL) в приватном PID namespace от UID агента:
PID1 и вызывающий процесс исключены ядром. Guard проверяет контейнер и supervisor.
Обычный tini здесь не подходит: его основной дочерний процесс был бы завершён отменой.
Фоновые процессы после операции тоже удаляются. Контейнер остаётся до release/простоя.

## Альтернативы

- Rootless Docker: уменьшает полномочия daemon на Linux, но требует отдельной настройки
  user namespaces/cgroups и проверки лимитов. Не подменяем текущий Desktop новым daemon
  ради первого прототипа; этот вариант остаётся кандидатом для демонстрационной Linux-машины.
- Подпроцесс на хосте: проще, но не отделяет файлы, сеть и ресурсы от машины пользователя.
- Удалять контейнер при каждом cancel: останавливает потомков, но теряет временную /work
  и нарушает выбранное сохранение завершённых правок.
- Persistent volume: переживает контейнер, но требует отдельной очистки и не даёт переносимого
  жёсткого лимита размера на текущем storage driver.

## Последствия и проверка

Компрометация менеджера означает риск для Docker-хоста. Текущая изоляция не заменяет
полный набор атак и сбоев C2-03/C2-05. После перезапуска менеджера сессии не восстанавливаются:
его оставшиеся контейнеры удаляются. Одноразовый Compose job sandbox-image проверяет
наличие исполнителя и pytest, затем завершается; это не постоянно работающий сервис.

Агент проверил: HTTP-файлы и команды, один result и SSE resume, повторы без исполнения,
отмену отделившегося setsid-потомка, сохранение файлов, read-only, сеть, размер /work,
UID/capabilities/seccomp, настройки CPU/RAM/PID, независимые сессии, release,
очистку при shutdown и после аварийного перезапуска. Прерывание публикации файла и
ускоренный idle cleanup проверены unit-тестами. Это не замер CPU/RAM и не fork-bomb тест.
