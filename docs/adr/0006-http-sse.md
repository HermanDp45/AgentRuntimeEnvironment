# ADR-0006: HTTP/JSON и SSE для обоих контрактов

- Статус: proposed для полного контракта; внутренняя часть v0 реализована и проверена
- Дата: 2026-11-06

## Контекст

ТЗ требует два версионируемых контракта, поток событий, отмену и один финальный
результат операции. Студент выбрал HTTP/JSON + SSE вместо WebSocket.

## Решение

Клиент ↔ сервер и харнес ↔ менеджер сандбоксов используют HTTP-запросы с JSON
для команд и SSE для событий. Это два разных контракта с собственными схемами.

Первый описывает подключение, сессию, задачу, подтверждение, события и отмену.
Второй — provision, exec (ReadFile / WriteFile / RunCommand), события,
ровно один result, collect, release и cancel.
Сообщения имеют версию. Внутренние маршруты и поля описаны в contracts/README.md;
клиентская часть пока не подключена к gateway.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| WebSocket | Двусторонний обмен по одному соединению | Команды и события требуют общего протокола соединения | Студент выбрал отдельные HTTP-команды и SSE |
| Только периодический опрос | Простой обмен запрос–ответ | Нет выбранного потока событий | Требуется SSE |

## Последствия

Команда и её наблюдение — отдельные операции. Потеря потока событий не доказывает,
что команда не исполнилась. Предлагаемый способ восстановления — запрос состояния
по идентификатору операции; повторное исполнение без установленного исхода запрещено.
Эту политику нужно проверить тестами идемпотентности и сбоев транспорта.

Проверки перед accepted: схемы обоих контрактов, упорядоченные события, один финальный
result, отсутствие повторного исполнения, отмена и различение классов ошибок.

Внутренняя часть проверена агентом: JSON Schema, HTTP/JSON, SSE с Last-Event-ID,
один result, повтор без запуска, cancel/timeout и классы ошибок.
[Реализация и ограничения](../../contracts/README.md),
[результаты](../../results/2026-11-06-sandbox-v0/README.md).
Клиент ↔ сервер пока только схема: поэтому ADR в целом остаётся proposed.
