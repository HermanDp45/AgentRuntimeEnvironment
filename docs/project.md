# Разбор проекта

## Задача простыми словами

Нужно собрать помощника, который умеет работать с файлами и запускать команды,
а затем доказать, что он работает предсказуемо. Модель уже существует;
обучать её и хранить веса в этом проекте не требуется.

Десктоп-клиент живёт на компьютере пользователя. Сервер запускается отдельно,
на Linux. Клиент показывает чат и события, сервер управляет выполнением.
На демонстрации это должны быть разные машины; Linux-ВМ тоже подходит.

## Кто за что отвечает

- **Клиент:** адрес и токен сервера, выбор папки, чат, отмена и переподключение.
  У него будет headless-режим для автоматических сценариев.
- **Gateway:** вход на сервер, сессии, сообщения и доставка событий клиенту.
- **Харнес:** собирает контекст для модели, принимает вызовы инструментов,
  запускает их через сандбокс и решает, продолжать ли цикл. Нужны ограничения
  на шаги и время, иначе ошибочная модель может зациклиться.
- **Менеджер сандбоксов:** создаёт изолированную среду, исполняет операции,
  отменяет команды и убирает ресурсы после сессии.
- **LLM-прокси:** единственная точка доступа к API модели. Ключ находится здесь,
  а не внутри сандбокса с командами агента.

Харнес не должен исполнять команды на хосте сервера. Разделение проверяется
контрактами и тестами, а не только соглашением в коде.

## Почему папка — самая сложная часть

Обычный bind mount Docker видит папку на сервере. Наша папка находится на Mac:
её нужно открыть серверу через сеть и смонтировать в `/work`.
Это именно монтирование, а не периодическое копирование файлов.

Нужно проверить доступ в обе стороны, read-only/read-write, защиту `.git`,
симлинки наружу и одновременную запись. При обрыве сервер не должен молча
писать в пустую локальную папку вместо исчезнувшего mount.
Операции должны завершаться понятной ошибкой за ограниченное время,
а пользователь — видеть причину остановки. После сессии сервер не хранит копию папки.

Первый кандидат — локальный WebDAV в клиенте и rclone/FUSE на Linux.
FUSE при этом нужен на Linux, а не на Mac. Обратное соединение или туннель,
права и кеширование сначала проверим отдельным экспериментом.
Этот вариант ещё не принят: см. [предложение ADR-0002](adr/0002-workdir-mount.md).

## Как докажем качество

**Инфраструктурные тесты** проверят ограничения, очистку, отмену,
сеть, ошибки и восстановление. **UI-тесты** — действия пользователя.
**БАФ** проверят самого агента: прочитать, найти, создать, отредактировать,
использовать инструмент, написать код, рассудить, свести несколько источников.

У курса 8 функций по 3 задания и 3 составные задачи. В официальном шаблоне
есть каталог формулировок, но полностью оформлен только пример Б1.1;
остальные фикстуры и чекеры нужно подготовить. Ещё нужны минимум одна своя
задача для каждой функции, своя функция из 3 задач и своя составная задача.
Получается не менее 39 задач на пару.

Цель — сравнить минимум 3 пары «харнес + LLM», по 3 повтора каждой задачи:
не менее 351 запуска. Для допуска в ТЗ отдельно упомянут минимум 2 пары;
планируем полный целевой объём. Финальные прогоны выполняются по запросу,
после оценки расхода токенов. CI использует mock/record-replay и не расходует API-бюджет.

Среда и задачи при сравнении фиксируются. Сохраняем успешность, время, токены,
разброс и причины ошибок. Потом проверяем составные задачи: помогают ли
результаты отдельных функций объяснить успех или сбой всей цепочки.

## Порядок реализации

1. **Подготовка:** среда, gateway, проверки и понятная документация — текущий этап.
2. **Первый сценарий:** харнес, proxy, сандбокс и протоколы; клиент подключается,
   видит события; раннер выполняет первые Б1–Б5.
3. **Удалённая папка:** эксперимент с mount на двух машинах, ADR,
   затем интеграция с клиентом и сандбоксом.
4. **Устойчивость:** лимиты, секреты, сетевая политика, отмена, обрывы,
   параллельные сессии и все три вида тестов в CI.
5. **Сравнение и защита:** полный набор БАФ, замеры, выбор пары, отчёт и объяснение решений.

Это рабочая последовательность; ориентиры чекпоинтов курса не являются
подтверждением готовности наших компонентов. Отметки — в [чеклисте](../TASKS.md).

## Что понадобится

- Сейчас: этот Mac, Git, uv, Make и запущенный Docker Desktop.
- Для удалённого сценария: Linux-сервер или ВМ с Docker, доступ по сети
  и возможностью использовать выбранный механизм монтирования.
- Для модели: API-адрес, токен и идентификатор разрешённой модели.
  Общие правила сейчас называют DeepSeek 4.1 / 4.0 Flash или модели не слабее
  DeepSeek Flash по Artificial Analysis Intelligence Index на дату выбора.
  До эксперимента перепроверяем доступность, рейтинг и условия курса;
  записываем версию, индекс и дату. Внутри эксперимента модель не меняем.
- Время и API-бюджет для повторных прогонов. Собственные GPU и веса для API-подхода не нужны.
- Подтверждение регистрации комбинации «харнес × сандбокс × монтирование» у курса:
  доступность такой комбинации не установлена, регистрацию выполняет студент.

Стек: Python для сервера, собственного харнеса и тестов, PySide6 для будущего клиента.
Конкретный запуск сандбоксов и оба транспорта оформим отдельными ADR после проверки.
Docker socket даёт широкие права на хосте: доступ к нему нельзя выдавать сандбоксу агента.

Арена не входит в основной объём задания A. AR-02 — возможный бонус,
который рассматриваем после основной системы.
