# Менеджер сандбоксов

Работающий прототип: HTTP/JSON + SSE, один Docker-контейнер на активную сессию.
Внутри Python, `/bin/sh` и pytest. LLM и настоящего монтирования Mac пока нет.

## Где что лежит

- `src/sandbox_manager/app.py` — HTTP и SSE, валидация через `contracts/`.
- `runtime.py` рядом — сессии, повторы, события, таймер, отмена; одна операция на сессию.
- `backend.py` рядом — создание контейнера и Docker exec; единственная точка доступа к Docker.
- `sandbox/sandbox_worker.py` — исполнитель внутри контейнера: файлы, shell, остановка процессов.
- `config.toml` — лимиты; `Dockerfile` — менеджер, `sandbox/Dockerfile` — среда агента.

## Как работает

`provision` создаёт контейнер и записывает синтетические файлы в tmpfs `/work`.
`exec` запускает инструмент; stdout/stderr передаются событиями, итог приходит отдельно.
Контейнер сохраняется между операциями. `collect` выгружает небольшие текстовые результаты,
`release` удаляет контейнер. Сообщения — в [контракте](../../contracts/README.md).

При cancel/timeout исполнитель останавливает все доступные процессы своего PID namespace,
кроме себя и PID1. Python PID1 остаётся жить и собирает осиротевших потомков;
записанные файлы остаются. Guard запрещает этот сигнал вне контейнера с ожидаемым PID1.
После обычной команды потомки тоже очищаются: фоновые службы в v0 не поддерживаются.

WriteFile сохраняет приватную копию старого текста в `/state` менеджера, затем пишет
новый текст в служебный файл рядом с целевым. SHA сверяется перед заменой;
публикация — атомарный rename, для нового файла — link без перезаписи.
Прерывание до публикации оставляет исходный файл; после неё остаётся новая версия.
Служебный файл и приватная копия удаляются при завершении. Полного отката команды нет.

## Ограничения и границы

По умолчанию: 1 CPU, 1 ГБ RAM без дополнительного swap, 128 PID,
`/work` 64 МиБ, `/tmp` 16 МиБ, операция до 120 с, простой до 30 минут.
До 4 сессий, 128 операций на сессию, 64 КиБ на текстовый файл и вывод команды.
После изменения config нужна пересборка менеджера. Collect принимает до 128 UTF-8
файлов и 512 записей каталогов.

Сандбокс: UID 10001, read-only root, без capabilities, no-new-privileges,
встроенный seccomp, network_mode none. Нет host bind mounts, Docker socket и ключа LLM.
Read-only-сессия имеет root-owned `/work`: файлы 0444, каталоги 0555 — run_command
тоже не может их изменить. Ограниченный `/tmp` доступен для записи.
Образ разрешается в image ID при старте менеджера; через API его менять нельзя.
Compose задаёт имя образа с префиксом проекта, чтобы параллельные запуски не
перетирали общий тег. При ручной пересборке образа нужно перезапустить менеджер.

Docker socket есть у **доверенного менеджера**, который работает как root.
Его компрометация затрагивает Docker-хост. Это локальная схема для Docker Desktop
и учебного Linux, API открыт только на loopback, авторизации пока нет.
Сравнение с rootless — [ADR-0007](../../docs/adr/0007-sandbox-v0.md).

`/work` временная: collect нужен **до** release. После удаления контейнера или
перезапуска менеджера файлы исчезают. Пользовательская папка здесь ещё не подключена;
для этой версии используйте синтетические фикстуры. Настоящее монтирование —
отдельный эксперимент [ADR-0002](../../docs/adr/0002-workdir-mount.md).

Сессии и события — в RAM. В приватной tmpfs `/state` — краткие JSONL-метаданные
(ID, инструмент, длительность, статус), без команд и текстов файлов;
свыше 1 МиБ журнал начинает новый файл. Это не будущая история чата в runs/.
При shutdown удаляются сессии, при старте — оставшиеся контейнеры только своего
namespace (метка are.owner). Одному namespace соответствует один менеджер.

## Проверка

Из корня проекта:

```bash
make setup
make test-ci
make up
make test-infra
uv run --frozen --offline python tests/infra/check_lifecycle.py
make down
```

Python-скрипт проверяет аварийный перезапуск и оставляет менеджер остановленным.
Сценарии используют собственные временные сессии. После установки зависимостей
и сборки образов ключ модели и внешняя сеть тестам не нужны.
