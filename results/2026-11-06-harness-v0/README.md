## Реальная модель

AIRI, Qwen/Qwen3-235B-A22B-Instruct-2507. В обычном Compose с локальным ключом
выполнен один read-only сценарий: note.txt содержит PORT=7319, модель должна
вызвать read_file и ответить только значением порта. Записи/команды проба отклоняет.

- live-read-dns-failure.json: первая попытка остановилась до модели из-за DNS контейнера.
- live-read.json: после временного DNS-обхода passed=true, ответ 7319,
  два обращения к модели, 1573 входных + 26 выходных токенов, 2.122 с на эту пробу.
  Это один функциональный пример, не замер производительности и не БАФ.
- build-production.txt: обычный Compose без mock LLM.
- dns-override.yml: диагностический снимок адреса, не постоянная конфигурация сервера.

На Mac inference.airi.net разрешался в 194.190.0.250 и отвечал по HTTPS.
В Docker 127.0.0.11 с внешними DNS 1.1.1.1/8.8.8.8 не разрешал ни провайдера, ни github.com.
Запросы без ключа подтвердили: после точечного extra_hosts HTTPS отвечает 404 на корень
(нормально для API). TLS не отключался; root filesystem оставался read-only.
Глобальные настройки Desktop не менялись, причины недоступности его DNS не устранены.

Команды эксперимента после make up и проверки актуального адреса провайдера на Mac:

```bash
docker compose -f docker-compose.yml -f results/2026-11-06-harness-v0/dns-override.yml up -d --wait --wait-timeout 45 llm-proxy
uv run --frozen --offline python services/harness/probe.py results/harness-read.json
make down
```

Снимок привязан к дате: не следует переносить старый IP в постоянный конфиг.
При исправном DNS overlay не нужен. Временный ключ остаётся только в .env и прокси.
Linux CI с mock LLM проверяется отдельно после публикации; реальный API в CI не вызывается.
