# Контракты v0

Источник схем — `v0.py` (Pydantic), общая проверка путей — `paths.py`.
JSON Schema обоих протоколов экспортируются командой:

```bash
uv run --frozen --offline python -m contracts.export
```

Тест проверяет соответствие схем моделям. Обязательны `version: "0"` и `type`;
неизвестные поля и операции запрещены. Идентификаторы — UUID.
Несовместимые изменения получат следующую версию.

## Харнес ↔ сандбокс: реализовано

Менеджер слушает `127.0.0.1:8081`. POST-запросы с JSON:

- `/v0/provision`: `type: provision`, `session_id`, `files` (путь → текст), `read_only`.
  Создаёт контейнер с временной учебной `/work`.
- `/v0/exec`: `type: exec`, `session_id`, `operation_id`, `operation`, `timeout_s`.
  Возвращает 202 и состояние; выполнение продолжается отдельно.
- `/v0/cancel`: `type: cancel`, `operation_id`. Останавливает операцию и ждёт завершения.
- `/v0/collect`: `type: collect`, `session_id`. Возвращает тексты файлов и SHA-256.
- `/v0/release`: `type: release`, `session_id`. Удаляет контейнер и состояние сессии.

Наблюдение методом GET:

- `/v0/operations/{operation_id}`: `state: running|finished`, итог в `result`.
- `/v0/operations/{operation_id}/events`: SSE `started`, `stdout`, `stderr`, один `result`.
  `id` равен `sequence`, счёт с 1 для каждой операции. `Last-Event-ID` или `?after=N`
  возвращает события после N. Обрыв SSE не отменяет выполнение.
- `/health`: HTTP 200, если Docker и закреплённый образ доступны.

Везде в POST нужен `version: "0"`. Возможные `operation`:

```json
{"kind":"ReadFile","path":"note.txt"}
{"kind":"WriteFile","path":"note.txt","content":"new text","expected_sha256":"missing"}
{"kind":"RunCommand","command":"python --version"}
```

Это три отдельных примера. `missing` означает создание нового файла;
для замены передаётся SHA-256 из ReadFile. Пути файловых операций ограничены `/work`:
без абсолютных путей, `..`, `.git`, симлинков и служебных `._are_*`.
Файловые операции поддерживают UTF-8 до 64 КиБ на файл. RunCommand видит также
read-only файлы образа; пользовательская папка и её `.git` ещё не монтируются.

## Повторы, ошибки и завершение

Один operation_id и те же параметры возвращают прежнее состояние без повторного
исполнения. Другие параметры с тем же ID дают 409. Аналогично работает provision.
В сессии одна операция; одновременная новая получает 409. Разные сессии независимы.
Повтор release успешен, повтор cancel завершённой операции возвращает прежний итог.
После release ID забываются; новые сессии используют новые UUID.

Итог: `status: ok|error|cancelled`, данные — `value`. При error обязательны
`error.kind`, `code`, `message`:

- `command`: ненулевой exit_code; stdout и stderr сохранены.
- `timeout`: время операции превышено, процессы остановлены.
- `sandbox`: неверный путь, конфликт SHA, запрет записи, лимит файла и другие ошибки инструмента.
- `transport`: Docker/исполнитель недоступен; успешная отмена не обещается.

HTTP-ошибки тоже имеют оболочку version/type/error: 422 — неверный запрос,
404 — неизвестный ID, 409 — конфликт, 503 — недоступность. Валидация не возвращает
содержимое входных файлов. Время ограничено меньшим из timeout_s и настройки менеджера
(120 с); socket-вызовы Docker имеют timeout 10 с. Если отмена ещё не завершена за 15 с,
возвращается 503 cancel_pending: нужно запросить состояние, не запускать новую команду.
Автоматических повторов исполнения нет. После обрыва сначала запрашивается состояние;
допустимо повторить **тот же** запрос с тем же ID.

Состояние и события живут в памяти менеджера. Его перезапуск удаляет оставшиеся
контейнеры своего namespace. Восстановления операций после падения пока нет:
один result гарантируется в живом менеджере, не между перезапусками.
При 404 нельзя считать, что команда не исполнялась.

## Клиент ↔ сервер: пока только схема

Определены session.create, task, approval, run.cancel, resume, session.close,
ответ session, события run.event и итог run.result. `run_id` — целая задача,
`operation_id` — один инструмент. События задачи имеют свой sequence.
Маршруты, авторизация и обработка этих сообщений появятся с харнесом и клиентом;
сейчас gateway реализует только `/health`.

Менеджер — внутренний доверенный компонент. Подтверждения записи и команд будет
проверять харнес перед `/v0/exec`; пользовательский approval пока не реализован.
